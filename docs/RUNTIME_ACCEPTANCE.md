# OpenKill 1080 验证与验收

本版优先完成启动管理和测试覆盖，再提供有限流量的性能测量工具。

## 自动验证

- 地址：空值、LAN CIDR、显式 IPv4、IPv6、通配监听、非法输入。
- 运行状态：有效生成配置中的地址、端口和密码；指定 procd 核心实例。
- 启动：过期检查不得修改新实例；失败不得覆盖正常检查点。
- 内核：官方 v1.19.30 基线和发布时最新稳定版，两种接管方式 × 两种协议栈 × IPv6 开关的配置校验。
- 实际进程：本地控制器认证、HTTP 代理转发和 DNS 响应。该测试不创建 TUN 或更改运行器路由。

IPK 和 APK 在测试通过后独立构建和发布。配置校验通过不等于协议已完成真实握手；附加字段无法充分确认时，界面显示“未验证”。

## 恢复语义

启动检查共享 90 秒等待预算，单次外部请求最多约 3 秒。配置生成、内核预检和防火墙命令不包含在这段等待预算内。

检查点保存有效 YAML、对应 OpenKill UCI 和内核摘要，权限仅限 root。只有全部就绪检查通过才更新。首次安装没有检查点时停止并保留错误；有检查点时只尝试恢复一次。自动恢复失败不再循环，明确手动启动后允许新的恢复周期。

内核更新先用候选内核校验实际配置，并保存 `.previous` 内核。跨内核恢复仅在上一内核摘要与检查点一致时允许。外部规则/订阅文件不包含在检查点中，损坏或缺失时预检可能拒绝恢复。

独立健康观察器每 60 秒检查一次核心进程和 API，连续三次失败记录错误；运行中进程退出由 procd 按有限次数重启，观察器不重复启动内核。耗时维护不会阻塞这个观察器。

## 软路由验证（需要实际设备，CI 不代替）

1. 记录固件、CPU、内存、防火墙后端、插件和内核版本，备份 OpenKill 配置。
2. 冷启动、重启、切换配置各执行至少 5 次，确认配置、PID、控制器、DNS、代理规则一致。
3. 分别测试 OpenKill 管理及 Mihomo 原生管理；后者必须使用 IPv4 TUN/混合模式，并检查双栈对应路由。两种管理方式互斥。
4. 故障测试：错误密码、端口占用、配置语法错误、缺失依赖、核心退出、停止期间旧检查仍在运行；确认至多恢复一次。
5. 验证 5 个实际节点：两个 IPv6 节点、三个 IPv4 节点；确认 A/AAAA、国内直连与国外代理。保留 IPv6，不修改其他固件服务以掩盖问题。
6. 观察 24 小时：异常退出次数、内存趋势、DNS 失败、延迟和后台 CPU。

## 吞吐验证

`scripts/measure-proxy.py` 在测试电脑上通过明确指定的 HTTP 代理下载同一个 HTTPS 文件，每轮最多 16 MiB/约 20 秒，共三轮。单次读取超时 5 秒，故总时间可能稍超预算。不会自动回退直连；环境代理不参与。目标 URL 和节点均需使用自己的测试资源。

```sh
python scripts/measure-proxy.py --proxy http://192.168.1.100:7893 --url https://YOUR-ENDPOINT/test-file
```

如代理要求认证，应使用现有安全的认证测试工具，不要为了测速开放无认证的公网监听。测试工具的匿名示例不要求更改正式配置。

比较同节点的显式代理与透明代理，固定出口、协议和时间段，同时记录单核 CPU、软中断、内存、重传和满载延迟。单连接与多连接分别测量；小流量测量只用于定位问题，不能证明可持续跑满带宽。

以实际结果决定 TUN 协议栈、MTU、测速周期和规则优化。没有实测证据前不统一调整系统网络参数，不把延迟评分当作吞吐评分。
